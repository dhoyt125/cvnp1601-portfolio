# Provisioning Summary

Ticket CVNP1601-W3-003 requested that a new Linux user, `devuser`, be provisioned with membership in the `developers` group and scoped sudo access to restart a single service. The `developers` group was created first with `groupadd developers`, followed by the user account itself using `useradd -m -G developers -s /bin/bash devuser`, which also created a home directory and assigned bash as the login shell. Group membership was verified with `id devuser`, confirming `devuser` was added as a supplementary member of `developers` alongside its own primary group. Rather than granting full sudo privileges, a targeted sudoers rule was written to a dedicated drop-in file, `/etc/sudoers.d/devuser-service-restart`, using `visudo` to safely validate syntax before saving. The rule authorized exactly one command with a full binary path and fixed arguments, `/usr/bin/systemctl restart nginx`, with no wildcards, so the account could not be used to start, stop, or check other services, nor restart any unit besides `nginx`. This design directly satisfied the ticket's security requirement that full sudo would over-grant access and that only one exact service action should be permitted. Testing confirmed the rule worked as intended: `sudo -u devuser sudo /usr/bin/systemctl restart nginx` succeeded, while `sudo -u devuser sudo /usr/bin/systemctl restart sshd` and `sudo -u devuser sudo /usr/bin/systemctl stop nginx` were both denied, proving the rule was scoped to one exact action rather than the whole service or command family. Final verification was performed with `sudo -u devuser sudo -l`, which listed only the single authorized command under `devuser`'s sudo privileges and confirmed no broader access existed. One non-security issue was encountered along the way: `/home/devuser` was unreadable to other users by design (mode `700`, owned by `devuser`), which was confirmed with `sudo ls -ld /home/devuser` rather than treated as a misconfiguration. All required evidence — account creation, group membership, the sudo rule, the allowed command, the denied command, and the `sudo -l` output — was captured to close out the ticket. After documentation was finalized, the environment was optionally cleaned up by removing the sudoers rule via `visudo`, deleting the account with `sudo userdel -r devuser`, and removing the group with `sudo groupdel developers`.
